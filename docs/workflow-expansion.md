# Workflow expansion — September 26, 2026

This release keeps **one workspace per account**. Implementation and verification use local synthetic data only. No hosted migration, deployment, Git push, or AI provider request was performed.

## Delivered behavior

- **Payment corrections:** an owner/admin or owning freelancer can correct an erroneously recorded receipt with a reason. The original payment remains, an immutable correction is added, and the invoice balance/status and PDF recompute from unreversed receipts. This is a bookkeeping correction, not a refund or money transfer. Identical request retries are safe; a second different correction is rejected.
- **Time billing:** completed work from one project/client can become an invoice draft in one transaction. Business work requires independent approval. Each entry is reserved once, with an immutable snapshot, and cannot be changed while reserved. Charges use exact minutes rounded to cents per entry. Delete an unissued draft or cancel an issued invoice to release time; cancelled history stays available. Legacy `invoice_id` links remain reserved. Time-generated lines are fixed; recreate a draft to change them.
- **Review inbox:** review captured expenses/time, independently approve or reject submissions, and follow up on personal or vendor bills. Rejected records can be corrected and resubmitted. The database now verifies the actual approval transition; the former policy could silently affect zero rows.
- **Money-out history:** status changes and allowlisted financial values are recorded without receipt paths, notes, or contact details. Paid/cancelled bills and approved expenses cannot be rewritten or deleted by browser clients. Expenses/vendors are archived and bills cancelled to preserve records. Vendor bill headers and lines save atomically and totals are calculated in the database. Payments require a recorded date and do not initiate transfers.
- **Duplicate protection:** personal bills reject an exact matching payee/name/date/amount/currency; vendor bills serialize duplicate vendor/bill numbers; receipts cannot be attached to a second active expense on creation. Bill, expense and vendor-bill creates now commit an immutable private request record alongside the financial record. Identical retries return the original ID without another history event, even after payment/archive; changed input and other actors are rejected. Forms retain their original request in memory, freeze fields after an uncertain save and offer an explicit retry. The expense form retains its uploaded receipt. This is not general fuzzy duplicate detection or document-content hashing.
- **Workspace registry:** stable organization IDs identify business workspaces and user IDs identify individual workspaces. A unique membership per user is backfilled and protected from client forgery. Protected legacy profile changes synchronize membership role/active state. Switching established workspaces requires a separate migration operation. Existing financial ownership columns/policies remain as a compatibility interface; this is not a wholesale ownership-column cutover.
- **Contacts:** one searchable, paginated, RLS-preserving directory over clients and vendors, with archived visibility and links to their editors. Existing IDs and roles remain distinct; possible duplicate people/companies are not automatically merged. Vendor location/payment-term fields now persist instead of being discarded. Vendor tax IDs are excluded from the common directory.
- **Settings and reporting:** validated preferences persist using atomic patches. New manual invoices use saved tax/currency/payment terms, including zero-day terms. Tax Prep separates calendar year, currency, and cash receipts versus issued invoices; reversed payments and draft/cancelled invoices are excluded. Cash reports do not invent payments for legacy PAID invoices. Expenses are captured records, not proof of payment or tax deductibility. Concurrent quarterly-reminder creation does not duplicate periods or replace existing amounts. Unsupported sales-tax placeholder totals are hidden.
- **Security:** per-request CSP nonces protect scripts, connections are limited to the configured Supabase origin, and page responses are private/no-store. Caller-supplied nonce headers are overwritten. Inline styles remain permitted for Radix positioning/charts/theme behavior; development alone permits script evaluation. Pages now render dynamically, with the associated server cost/cache tradeoff. Deferred accounting/payroll/inventory modules remain disabled; database grants also deny their browser writes, while historical reads/exports require the manager and matching parent ownership. Team permission management remains deferred.

## Remaining boundaries and release gates

1. **Production readiness is not established by local tests.** Hosted upgrade/restore rehearsal, representative historical-data inspection, production migration-history reconciliation/recovery point, older-client inventory (including iOS), preview-domain checks, hosted email/expiry flows, and production security settings remain pending under the local-only instruction. The app and all eleven timestamped workflow migrations must release together; old direct-write clients are incompatible.
2. Legacy payment reconciliation now has an explicit evidence-review workflow; it still requires the reviewer to verify actual evidence. No receipts, historical approvals, missing vendor fields, or invalid historical records were fabricated or rewritten. Existing older receipt URLs may remain valid until their original expiry.
3. The tax estimator is explicitly illustrative, single-filer, USD-only, and limited to reviewed 2025/2026 rules. It excludes credits, QBI, capital gains, other wages, additional Medicare tax, state tax, retirement deductions, disaster relief and safe-harbor calculations. Saved date formats apply to financial lists and history. A separate Workspace reports tab uses the saved fiscal start month or a calendar year; tax filings and estimates retain calendar-year scope. CSV dates remain ISO, and PDF formatting is unchanged. Notifications are stored preferences, not an email-delivery implementation.
4. Advanced accounting posting, payroll calculation/payment, inventory changes and team administration require dedicated audited commands before re-enabling. Purchase-order commands have their own local validation below; remaining legacy modules are not certified by the vendor-bill workflow. This release does not certify Amountly as a complete accounting/payroll/tax system.
5. Live AI success/failure remains unverified; the AI provider is deliberately disabled locally. API retry/concurrency tests and browser response-loss checks for payments and purchase orders pass.

## Retry recovery follow-up (after fcddc0f)

`20260926044850_retryable_money_capture.sql` adds the private request ledger and authenticated create commands. All request fields are allowlisted; ownership is derived from the authenticated actor; currency, amount precision, dates, initial state, parent workspace and receipt paths are checked. Anonymous, inactive and cross-account calls are denied. The underlying vendor insertion helper is no longer callable by browser roles. The ledger has no browser read/write grants or public REST exposure.

The ledger preserves the original request, rather than comparing against a financial record that may subsequently change. Three simultaneous identical bill requests produce one record/event. Failed validation rolls back both record and ledger. An uncertain request stays locked even if a later retry is denied, since that denial does not establish the earlier outcome. A definite first rejection allows correction and a new request ID. Request payloads are kept only in the private database and mounted form memory, never localStorage/sessionStorage. Leaving/reloading the page loses the in-memory retry request; review the saved list before entering another record.

Validation: `npm run test:capture` covers immutable retry input, later denial, corrected requests and simultaneous submission. Fresh-database and upgrade/restore suites pass with capture concurrency, altered-payload rejection, inactive/foreign-user and receipt-boundary tests.
